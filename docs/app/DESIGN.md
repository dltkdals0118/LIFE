# LIFE 웹 프로그램 — 제품·시뮬레이션·게임 설계 v0.2

작성 2026-11-02. 상태: 검토 가능한 설계 초안. 구현·배포 전.
사용자 요청: Notion처럼 유연한 개인 공간, 상황에 반응하는 플랜 ABC, 성공 가능성과 실패 대안, 분야별 레벨·퀘스트·보상, GitHub URL로 접근하는 웹 UI.

## 1. 제품의 중심

**현재 상황을 기록하면 선택 가능한 경로가 갱신되고, 오늘의 작은 퀘스트가 장기 목표에 연결되는 개인 인생 설계 공간.**

반복 흐름: 관측 입력 → 영향받는 계획 재계산 → A/B/C 비교 → 사용자 선택 → 오늘 할 퀘스트 → 결과 기록 → 회고와 대안 갱신.
계획 작성 자체보다 현실이 바뀌었을 때 다음 행동을 찾는 데 가치를 둔다. 모든 분야는 공통 목표·계획·퀘스트 구조를 쓰며 재정·시간처럼 계산 가능한 분야에는 전용 계산기를 연결한다.

### 제품 성공 기준

- 오늘 할 일을 3개 이내로 제안하고, 각 행동이 어느 목표에 도움이 되는지 설명한다.
- 새 현금·일정·결과를 넣었을 때 영향을 받는 계획과 바뀐 이유를 볼 수 있다.
- 실패나 보류 뒤 최소 행동 또는 대체 경로로 이어진다.
- 기록은 일 2분, 회고는 주 10분을 설계 목표로 삼고 실제 소요시간으로 검토한다.
- 재미 평가는 사용자 주간 자기보고로 확인한다. 접속 횟수나 XP 증가만으로 성공을 판단하지 않는다.

## 2. Notion에서 가져올 사용성

왼쪽에는 오늘·인생 지도·계획·퀘스트·기록·회고·설정을 둔다. 가운데는 문서와 데이터베이스 뷰, 오른쪽은 선택한 항목의 근거·영향·다음 행동 패널이다.

각 분야 페이지에는 설명, 목표 목록, 관련 퀘스트 보드, 지표, 메모 블록을 배치한다. 같은 퀘스트를 표·칸반·달력에서 조회한다. 필터와 정렬은 저장된 뷰이며 데이터를 복제하지 않는다.
초기 블록은 제목·문단·체크리스트·링크·지표·연결된 목록으로 한정한다. 임의 수식 언어, 실시간 공동편집, Notion 전체 편집기 복제는 후속 범위다.

### 확정된 시각 방향 — 2026-11-02 사용자 응답

Notion처럼 차분한 문서 공간을 유지하고 RPG 성장은 직관적인 도형과 진행 경로로 보여준다. 밝은 중립 배경·여백·절제된 분야별 강조색을 기본안으로 둔다. 구체적인 색과 아이콘은 화면 설계에서 결정한다.

| 전달할 정보 | 기본 시각화 | 세부 정보 |
|---|---|---|
| 분야별 성장 | 분야 카드의 레벨·XP 막대·획득 배지 | 누적 활동과 다음 레벨 조건 |
| 장기 목표 | 완료·진행·잠긴 노드가 이어지는 성장 지도 | 노드 선택 시 선행 조건·연결 퀘스트 |
| 플랜 ABC | 공통 출발점에서 갈라지는 경로와 현재 위치 | 전환 조건, 돈·시간 비용, 결과 범위 |
| 오늘의 행동 | 완료 기준과 예상 시간이 보이는 퀘스트 카드 | 최소 버전과 막혔을 때 대안 |
| 자원 변화 | 현금 추이·시간 예산 막대 | 날짜·단위·실제/가정·누락 표시 |
| 보상 | 획득/사용 가능/예산 대기 카드 | 잠금 해제 조건과 사용 이력 |

그래프는 실제 데이터의 의미와 단위를 보존한다. 분야 레벨을 서로 비교하는 능력 레이더 차트 대신 독립된 진행 막대를 쓴다. 미확인 값은 빈칸 설명으로 표시하고 그래프를 임의로 연결하지 않는다. 지도는 텍스트 목록으로도 접근 가능하게 하고 모바일에서는 선택한 분야/경로만 펼친다. 완료 연출은 짧고 조용하게, 큰 축하 연출은 선택 사항으로 둔다.

| 화면 | 핵심 내용 | 주요 조작 |

| 인생 지도 | 재정·경력·학습·생활/주거·회복·관계·창작·취미의 성장 경로 | 분야 추가, 목표 연결, 진행 근거 열기 |

| 주간 회고 | 진행, 장애물, 예측과 실제 차이, 다음 주 부담 | 유지·축소·교체 결정 |
| 보상함 | 분야 레벨, 획득 보상, 개인 보상 목록 | 외형 선택, 보상 사용 기록 |

오늘 화면 예시 구조:

```text

현금: 가상 예시 300만원 · 예시 기준일    [근거]
```

금액·경험치 예시는 서로 다른 의미로 표시한다. 실제 잔액과 예상 잔액에는 각각 기준일과 시뮬레이션 표시를 붙인다. 모바일은 오늘·지도·기록·회고를 하단 탐색으로 제공하고 큰 비교표는 플랜별 카드로 전환한다. 색상 외 텍스트 상태, 키보드 조작, 동작 줄이기를 지원한다.

## 4. 목표와 플랜 ABC

목표는 원하는 결과·기한·측정 기준·최소 허용 결과·우선순위·지킬 제약을 가진다.
**A는 현재 선택한 경로, B는 대체 경로, C는 최소 목표를 지키는 경로**라는 기본 템플릿이다. 사용자가 이름과 역할을 바꿀 수 있다. 기존 시뮬레이션의 A=현재 유지/B=안정/C=성장과 별개이며 기존 경로명을 자동 재해석하지 않는다.

각 플랜 필드:

- 성공 조건: 지표·비교 연산·목표값·기간·근거 요구 수준.
- 착수 조건: 필요한 돈·시간·준비물·선행 퀘스트.
- 비용과 효과: 일회/반복 비용, 예상 시간, 기대 결과, 지연 기간, 범위와 출처.
- 포기할 것: 다른 목표의 지연·유동성 감소·일정 부담.
- 전환 규칙: 관측할 지표, 임계값, 지속 기간, 대체 플랜, 전환 비용과 소요 시간.
- 중단 조건: 사용자가 정한 한계, 필수 의무 위반 여부, 종료·회복 행동.
- 실패 후 행동: 최소 행동으로 축소, B로 전환, C로 전환, 재설계 중 어느 것인지.

규칙 예시(값은 사용자 결정 전 템플릿): `available_hours < plan.required_hours`가 확인되면 시간 위반을 표시하고 더 작은 B를 제안한다. 미확인 값은 false나 0으로 처리하지 않고 '판정 보류'다.
상태가 조금 변할 때마다 전환하지 않도록 규칙에 연속 관측 횟수·재검토 날짜·복귀 조건을 둔다. 여러 조건이 겹치면 필수 의무 → 사용자 우선순위 → 비용/시간 순으로 제안을 정렬한다. 충돌은 설명하고 사용자가 선택한다.
시스템은 재계산과 추천까지 수행한다. 실제 플랜 전환은 사용자가 채택하며 기존 진행·보상·사용 자원은 이력으로 남는다. B도 조건을 충족하지 않으면 '실행 가능한 대안 없음'과 부족 자원을 표시한다.

## 5. 성공률과 불확실성

성공의 사건부터 정의한다. '좋은 인생 80%' 대신 '11월 말까지 정한 절감액 달성'처럼 기간과 판정 기준을 가진 사건만 평가한다.

| 근거 상태 | 표시 | 계산과 제한 |
|---|---|---|
| 이력 부족 | 성공률 미산정 | 부족한 데이터·착수 조건·자원 여유·실패 대안 표시 |
| 반복 행동 기록 | 최근 완료 6/10회 등의 관측 빈도 | 기간·표본·보류/실패 기준을 함께 표시, 예측 확률로 단정하지 않음 |
| 명시적 분포 가정 | 가정 기반 달성 비율 | 모델·분포 출처·표본 수·seed·민감도 표시 |
| 충분한 예측/결과 이력 | 검증된 예측 모델의 확률·불확실성 | 시간순 검증, 보정 평가, 실패 사례를 공개한 경우에만 활성화 |

초기 시뮬레이터는 보수·기준·낙관의 **조건별 결과**를 비교한다. 3개 중 2개 달성했다고 성공률 67%로 표시하지 않는다. XP·레벨·자신감 점수를 성공 확률로 변환하지 않는다.

확률 기능의 후속 출시 조건: 비교 가능한 관측의 정의, 누락/중단 처리 규칙, 시간순 검증 데이터, 기준 모델 비교, Brier score와 보정 오차 평가, 사전 정의한 허용 기준 충족. 표본 수만 넘었다고 활성화하지 않는다. AI가 제시한 확률은 검증 없이 계산 결과로 채택하지 않는다.
몬테카를로 결과는 `성공 조건 충족 경로 수 / 생성 경로 수`다. 입력 분포의 근거가 없으면 실행을 보류하거나 사용자가 만든 가상 실험으로 표시한다. 돈·시간·수입이 공유하는 원인은 함께 변동시켜 독립 가정의 오류를 피한다.

## 6. 시뮬레이션 엔진

입력: 상태 snapshot + 플랜 revision + 가정 + 달력 + model version. 출력: 기간별 자원 원장, 성공 조건 판정, 제약 위반 시점, 미확인 영향, 대안 실행 가능성.

- 현금: 기초 잔액 + 외부 유입 − 외부 유출. 자기 계좌 이동은 자산별 잔액만 바꾸고 합산 현금을 줄이지 않는다.
- 포커: 통장 송금/회수와 플랫폼 손익을 분리한다. 가계부 포함 거래를 추가 가산하지 않는다.
- 시간: 근무·통근·회복·필수 일정 뒤의 여유와 퀘스트 요구시간을 비교한다. 동시 수행 불가 활동을 중첩 배정하지 않는다.
- 미래의 급여·비용은 예정일에 반영한다. 월 총액만으로 월중 현금 부족을 숨기지 않는다.
- 실측이 바뀌면 의존하는 결과를 갱신 필요로 표시한다. 과거 결과는 입력 hash와 버전을 유지한다.
- 실패 시 이미 발생한 비용은 보존하고, 대안에는 전환 비용·대기시간을 더한다. 모든 플랜의 수익을 동시에 합하지 않는다.
- 실제 사건과 사용자가 넣은 가상 사건은 별도 이벤트다. 가상 실행은 실제 퀘스트 완료·XP 지급을 만들지 않는다.

## 7. 퀘스트와 재미

퀘스트 종류: 실행(조건 변경), 관측(정보 확인), 준비(선행 조건), 회복(부담 조정), 도전(결과물), 회고(학습).
필드: 분야·목표·플랜·반복 주기·예상 시간·완료 기준·증빙 수준·마감·최소 버전·대안·XP·보상·실제 결과.
상태: 제안 → 수락 → 진행 → 완료. 진행 중 막힘·보류·취소로 이동 가능. 실패는 원래 판정 기준 미달이라는 결과로 기록하며 다음 행동을 연결한다. 기한 경과만으로 벌점을 주지 않는다.

### 성장과 보상 초안

분야별 레벨은 **해당 분야에서 쌓은 실행·학습 경험**이다. 건강 상태, 재산 규모, 사람의 가치나 전문가 자격을 뜻하지 않는다. 분야 이름도 '건강 점수'보다 '회복 습관'처럼 행동 중심으로 둔다.

- 퀘스트 XP 초안: 관측 5, 일반 실행 15, 결과물 30, 주간 회고 10. 시간과 지출 규모에 비례해 무제한 지급하지 않는다.
- 레벨 초안: 누적 XP `50 × (L−1) × L` 이상이면 Lv.L. Lv.1=0, Lv.2=100, Lv.3=300. 값은 재미 조정용 가정이며 플레이 테스트 뒤 변경한다.
- 핵심 역량 배지는 XP 외에 지정 결과물이 있어야 열린다. 예: 월 마감 1회 완료 배지. 현재 사용자 과거 경력은 별도 프로필로 보존하며 낮은 시작 레벨을 실력 부족으로 해석하지 않는다.
- 완료 보상은 즉시 작게, 주간에는 챕터 진척·회고 카드, 장기에는 분야별 지도 확장·외형·칭호를 제공한다.
- 같은 반복 퀘스트는 기간당 한 번 보상한다. 하위 퀘스트 쪼개기는 부모 보상 한도를 공유한다. 완료 취소 시 보상 원장을 역거래로 보정한다.
- 연속 출석 대신 주간 유연 목표를 쓴다. 쉬는 날을 허용하고 미완료로 누적 XP를 깎지 않는다.
- 계획 실패 후 근거를 남기고 대안을 선택한 회고도 정해진 한도 내에서 보상한다. 결과가 통제 밖에 있어도 학습과 실행은 남는다.
- 실제 돈이 드는 개인 보상은 별도 예산·예정 지출로 기록한다. 가상 포인트가 현금을 만들거나 소비 예산을 자동 증액하지 않는다.
- 포커 손익·판돈·플레이량에 XP를 지급하지 않는다. 기록·회고에만 보상을 연결하고 사용자 제약을 유지한다.

재미의 축은 선택(경로를 고름), 성장(완료 근거가 쌓임), 발견(새 대안을 찾음), 마무리(작은 행동이 끝남)이다. 확률형 유료 보상·순위 경쟁·쉬면 소멸하는 보상은 초기 설계에서 제외한다.

### 두 종류의 보상 — 첫 버전 필수

게임 보상은 배지·칭호·지도 장식·테마를 제공한다. 현실 보상은 사용자가 원하는 활동·경험·물건을 직접 등록한다. 예시는 산책 시간, 영화 보기, 사고 싶은 물건이며 실제 목록과 금액은 사용자가 정한다.

XP는 성장 이력이고 소비하지 않는다. 보상은 지정한 퀘스트 묶음·마일스톤으로 잠금 해제한다. 첫 버전에는 별도의 교환 화폐를 추가하지 않아 XP와 현금의 의미가 섞이지 않게 한다.

현실 보상 흐름: 등록 → 조건 달성 → 예산/시간 확인 → 예약 → 사용 완료. 무료 보상도 필요한 시간을 확인한다. 유료 보상에는 예상 금액·예산 항목·예약 금액·실제 결제 연결을 둔다. 예산을 정하지 않았으면 '예산 확인 필요'이고, 잠금 해제만으로 구매하거나 현금을 차감하지 않는다.
예약은 쓸 수 있는 보상 예산을 줄이고 실제 현금은 결제 기록 시 한 번 차감한다. 이미 가져온 가계부 결제와 연결되면 새 지출을 만들지 않는다. 예약 취소는 예약 예산만 돌려주며 실제 환불은 별도 거래로 처리한다.
온라인 서버에서 보상 예약을 확정해 두 기기가 같은 예산을 중복 사용하지 않도록 한다. 오프라인에서는 예약 요청을 임시 저장하며 확정으로 표시하지 않는다. 이미 사용한 보상은 퀘스트 완료 정정으로 지우지 않고, 달성 조건 변경 사실을 이력에 남긴다.

## 8. 데이터 모델과 상태 일관성

| 객체 | 핵심 필드·관계 |

| Source / Fact | 기존 ID·출처·기준일·kind·review_status 보존 |
| StateSnapshot | fact_ids, 유효 날짜, 미확인, 포함 자산 범위, revision |
| Domain / Page / Block | 분야, 문서, 순서, 블록 유형, 연결된 뷰 |
| Goal | 분야, 성공/최소 조건, 기간, 우선순위, 제약 |
| Plan / PlanRevision | goal_id, A/B/C 역할, 비용·시간·조건, 선택 이력 |
| TransitionRule | from/to, 조건식, 관측 횟수, 복귀 조건, 실행 비용 |
| Quest / Occurrence | 플랜, 완료 기준, 반복 인스턴스, 상태, 중복 방지 키 |
| Observation / Event | 실제 결과, 출처, 기록 시점과 유효 시점, 정정 대상 |
| SimulationRun | snapshot/model/plan 버전, 가정, seed, 결과, input_hash |
| RewardEntry | occurrence_id, 지급/취소, XP·외형, 중복 방지 키 |
| Review / Decision | 비교한 경로, 선택 이유, 다음 점검, 결과 |
| Account / Workspace | 로그인 주체, workspace 소유자, 데이터 접근 범위 |
| Mutation / SyncCursor | 요청 ID, device_id, base_revision, 서버 순서, 전송 상태 |
| RewardDefinition / Redemption | 유형, 해제 조건, 예약/사용 상태, 예상 비용·시간, 연결 거래 |
| RewardBudget / Reservation | 기간·예산 항목, 예약액, 만료/취소, 실제 지출 연결 |

반복 템플릿 수정은 과거 인스턴스를 바꾸지 않는다. 퀘스트 완료와 보상 지급은 한 저장 트랜잭션으로 처리하고 재시도해도 중복 지급하지 않는다. 실제 기록 수정은 새 revision과 보상 조정을 만들며 지표 변경만으로 과거 완료를 조용히 취소하지 않는다.
가져오기는 검증 → 차이 미리보기 → 적용 → 새 snapshot의 순서다. ID 충돌·단위 혼합·깨진 참조는 적용 전에 보여준다.

## 9. GitHub URL과 개인 데이터

프로젝트 저장소는 **https://github.com/dltkdals0118/LIFE**로 확정됐다. 웹 UI의 GitHub Pages 주소 후보는 `https://dltkdals0118.github.io/LIFE/`이며 아직 배포하지 않았다. 앱 전용 빌드 산출물만 배포 대상으로 지정한다.
Pages는 정적 HTML/CSS/JavaScript 호스팅이므로 화면과 브라우저 계산기를 올린다. 개인 기록은 빌드 파일에 넣지 않는다. 공개 가능한 앱 코드·가상 데모 데이터만 배포 산출물에 포함한다. 개인 기록은 인증된 데이터 저장소에 두고 공개 코드와 분리한다.

**휴대폰·PC 자동 동기화는 첫 버전 필수**로 확정됐다. 기본 구조는 GitHub Pages 웹 UI + 인증 서비스 + 비공개 데이터 API/DB다. 두 기기에서 같은 계정으로 로그인하면 같은 workspace를 읽고 쓴다. 외부 저장 서비스 업체·요금제·로그인 방식은 다음 기술 설계에서 비교해 결정하며, 아직 계정 생성·데이터 업로드는 하지 않았다.

앱 운영 데이터의 정본은 서버 DB다. 브라우저 IndexedDB는 캐시·미전송 변경 큐로 사용한다. LIFE 파일은 가져오기 전 기록의 정본이자 과거 보관 자료이며, 수입 후 앱의 변경을 자동으로 역반영하지 않는다. 로컬 기록을 계속 수정했다면 재수입 시 원본 ID·revision을 비교해 충돌을 검토한다. 앱 기록 내보내기와 복원도 지원한다.

데이터 흐름: LIFE JSON/CSV → 검증·미리보기 → 인증된 서버 workspace에 수입 → 각 기기 캐시. 실제 가져오기 시 업로드되는 항목과 저장 대상을 사용자에게 보여준다. 공개 웹 빌드에는 개인 기록·증빙·관리 키·GitHub 접근 토큰을 포함하지 않는다.

### 동기화 동작 계약

- 로컬 변경을 즉시 표시하고 미전송 큐에 저장한다. 온라인 저장은 서버 확인 후 '동기화됨'으로 전환한다. 기본 설계 목표는 정상 네트워크에서 다른 활성 기기에 5초 이내 반영이며 구현 후 측정한다.
- 변경 알림 또는 주기적 증분 조회, 화면 재진입·네트워크 복구 시 조회를 조합한다. 백그라운드에서 항상 실행된다고 가정하지 않는다.
- 각 변경에 고유 요청 ID와 base_revision을 부여한다. 서버는 재전송을 중복 처리하지 않고 서버 순서로 동기화한다. 기기 시계로 수정 우선순위를 정하지 않는다.
- 독립된 관측 추가는 함께 보존한다. 같은 필드의 동시 수정은 이전/서버/내 값을 보여주고 선택하게 한다. 현금 값·계획·금액은 마지막 저장으로 조용히 덮지 않는다.
- 같은 퀘스트 회차를 두 기기에서 완료해도 서버 트랜잭션과 고유 제약으로 완료·XP를 한 번만 반영한다. 오프라인 XP는 임시 표시다. 완료와 취소가 충돌하면 확인 전까지 보상 확정을 보류한다.
- 삭제는 삭제 이력을 전달해 오프라인 기기가 옛 항목을 되살리지 못하게 한다. 오래된 큐와 스키마 불일치는 자동 적용 대신 복구 화면으로 연결한다.
- 화면에는 '동기화됨 / 기기에 저장됨·전송 대기 / 충돌 확인 / 연결 필요'를 표시한다. 로그인이 만료되면 큐를 보존하고 재로그인을 요청한다. 계정 변경 시 다른 계정의 큐를 전송하지 않는다.
- API는 모든 읽기·쓰기에서 workspace 소유 권한을 검사한다. 로그아웃 시 해당 계정 캐시를 정리하되 미전송 변경이 있으면 내보내기·재로그인·삭제 중 선택할 수 있게 한다.
- 데이터 내보내기와 서버 백업 복원 절차를 별도로 둔다. 동기화는 삭제·오입력도 전달하므로 백업을 대체하지 않는다.

기술 구성 제안: TypeScript 웹 클라이언트 + 프레임워크 UI + 독립 계산 모듈 + 저장 어댑터 + 배포용 정적 빌드. 특정 라이브러리와 버전은 구현 시작 시 공식 문서로 검증해 고정한다. 경로는 Pages 하위 경로와 직접 접근을 지원하도록 설계한다.

## 11. 구현 순서와 인수 조건

| 단계 | 범위 | 완료 기준 |
|---|---|---|
| D0 설계 검토 | 이 문서, 사용자 선호, 데이터 경계 | 핵심 흐름·확률 의미·보상 방향 결정 |
| D1 화면 프로토타입 | 합성 데이터로 오늘→ABC→퀘스트→회고 | 주요 흐름을 클릭하며 설명 가능, 모바일 조작 가능 |
| D2 실행 가능한 MVP | 로그인·서버 DB·PC/휴대폰 동기화, 가져오기, 목표/ABC, 퀘스트, 시각적 성장, 게임/현실 보상, 백업 | 두 기기에서 1주 사용 가능, 동시 완료 중복 없음, 오프라인 복구·권한 검사·보상 예산 검증 |
| D3 반응형 계획 엔진 | 현금·시간 계산, 조건 비교, 전환 제안, 결정 이력 | 새 관측→영향 설명→대안 선택을 재현, 불가능한 플랜 표시 |
| D4 검증·배포 | 개인정보 없는 빌드, 접근성, Pages | 공개 산출물에 개인 기록 없음, URL 직접 접근·복원 검증 |
| D5 고도화 | 확률 모델, AI 보조, 성장 지도·보상 연출 확장 | 근거 검증·실사용 평가·접근성 조건 충족 |

초기 MVP의 성공률 영역은 미산정·관측 빈도와 조건 충족 상태를 제공한다. 정교한 예측 모델·복잡한 장기 분기·AI 자동 설계는 단계적으로 추가한다. 전체 인생을 한 번에 자동 판단하는 기능은 개발 목표로 삼지 않는다.

### 필수 검증 시나리오

1. 중복 자료 수입과 완료 버튼 재시도에도 거래·XP가 늘어나지 않는다.
2. null 잔액·수면을 0으로 계산하지 않고 영향을 받는 판정을 보류한다.
3. 동일한 자산 이동이 여러 입력 자료에 있어도 현금흐름은 한 번 반영한다.
4. A 실패 뒤 B 전환에서 이미 지출한 비용과 전환 비용이 유지된다.
5. 현금 조건을 통과해도 시간 제약 위반이면 실행 가능으로 표시하지 않는다.
6. 가상 실행에서는 실제 잔액·완료·보상이 바뀌지 않는다.
7. 완료 취소·데이터 정정·백업 복원 뒤 보상과 상태가 일치한다.
8. 공개 빌드·데모·로그에는 실제 LIFE 데이터가 들어가지 않는다.
9. 휴대폰에서 완료한 퀘스트가 PC에 반영되고 두 기기 동시 완료에도 XP가 한 번만 지급된다.
10. 오프라인 기록 후 재연결·로그인 만료·동시 수정·삭제 충돌에서 기록이 유실되거나 부활하지 않는다.
11. 다른 계정의 workspace ID를 지정해도 데이터를 읽거나 쓸 수 없다.
12. 보상 예약·가계부 결제 연결·환불이 예산과 현금에 중복 반영되지 않는다.

## 12. 확정된 제품 선택과 다음 설계

2026-11-02 사용자 응답으로 **Notion처럼 차분한 화면 + 직관적인 RPG 시각화**, **휴대폰·PC 자동 동기화**, **게임 보상과 현실 보상 모두**를 확정했다. v0.1의 기기 단독 저장·동기화 후순위 제안은 대체됐다.

다음 설계 산출물은 PC/모바일 주요 화면 와이어프레임, 인증·DB 서비스 비교와 비용 범위, 데이터 스키마·API·충돌 처리 상세다. 오늘→성장 지도→ABC 비교→보상 사용 흐름을 우선 검토한다. 구체적 보상 목록·월 보상 예산·경험치 수치는 미확정이며 사용자 생활 목표를 자동 변경하지 않는다.
